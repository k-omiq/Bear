# Windows and Linux installation validation, 2026-09-26

## Environments and result boundaries

The development host was a Mac17,3 MacBook Air with an Apple M5, 32 GiB RAM, macOS 27.0 (26A428), arm64, Rust 1.96.0, Node 26.3.0 and npm 11.16.0. Its graphics device reported Metal 4. Colima ran an Ubuntu 22.04.5 LTS `linux/amd64` container under QEMU emulation. The container reported `x86_64`/`amd64`, with neither `/dev/dri` nor `/dev/nvidia0`. No locally controlled Windows machine or VM, Linux desktop, or Linux GPU was available. The container was **not** an installed Linux desktop test.

No current-branch NSIS, AppImage or Debian package was produced on the Mac host. The Windows and Linux release workflow builds on native GitHub runners. A manual `validate_only` run builds and inspects artifacts while skipping the publish job. [Run 36217230873](https://github.com/k-omiq/manga-cleaner/actions/runs/36217230873) passed package inspections on `windows-2025-vs2026`, Ubuntu 22.04 x64, and macOS arm64 runners. [Run 36219174240](https://github.com/k-omiq/manga-cleaner/actions/runs/36219174240) additionally passed the Windows silent installation check; all three build jobs succeeded and Publish to R2 was skipped. These runs did not launch a desktop GUI or install models.

## Confirmed defect and fixes

The local `scripts/release.sh` path used a nonexistent `npm run tauri build` command, looked for bundles under `src-tauri/target` even though this workspace emits them under `target/<triple>`, and did not stage the frozen cloud helper or `uv`. A release from that path could fail before publishing or produce an installer without setup helpers. It now freezes and smoke tests the cloud helper, stages managed Python's `uv`, builds with `npx tauri build --target <triple>`, and reads the correct bundle directory. Its Python 3.11+ requirement is explicit.

`src-tauri/build.rs` now refuses release builds unless both generated helper binaries and their `bundle.externalBin` declarations exist. The tagged release workflow now checks the NSIS listing for both helpers, the four app-local VC++ runtime DLLs, SAM setup sources, and the updater signature. For Linux it extracts both the `.deb` and `.AppImage`, checks executable helpers and the bundled FLUX/SAM source files in each, prints Debian dependencies, and checks the AppImage signature. These checks inspect artifacts; they do not run model installation or inference.

The first build-only [CI run 36217069407](https://github.com/k-omiq/manga-cleaner/actions/runs/36217069407) found another fresh-build defect: all three frozen provisioners failed self-check because the Modal SAM seed referenced files absent from the PyInstaller bundle. The freeze script now includes the exact SAM bootstrap, ONNX export, and synthetic fixture files. The second run passed the frozen helper self-check on all three runners before building packages.

A later [CI run 36218366939](https://github.com/k-omiq/manga-cleaner/actions/runs/36218366939) passed all package builds and inspections but exposed an error in the new Windows smoke-test harness: after invoking NSIS, PowerShell reported a blank `$LASTEXITCODE`, so the script failed before inspecting the installed files. The harness now starts the NSIS process with `ProcessStartInfo`, waits for it, and reads its exit code directly. That failed step alone does not establish whether the installer succeeded or failed.

## Commands and observed evidence

- `bash -n scripts/release.sh`, `git diff --check`, and Ruby `YAML.load_file('.github/workflows/release.yml')` passed.
- `colima start --arch aarch64 --cpu 4 --memory 8 --disk 20` succeeded. `docker run --rm --platform linux/amd64 ubuntu:22.04 ...` reported Ubuntu 22.04.5 LTS, `x86_64`, `amd64`, and no DRI or NVIDIA device. This verifies an emulated container is available; it does not verify a package or app launch.
- A fresh **macOS** release `.app` was built with `npx tauri build --target aarch64-apple-darwin --bundles app` after staging the existing frozen provisioner and a local `uv` binary as external binaries, and temporarily disabling updater artifacts because the signing key was not supplied. It completed in 1m 11s and produced a 102 MB app. The app contained executable `manga-cleaner-provisioner` and `manga-cleaner-uv`, `sidecar/bootstrap.py`, `sidecar/pyproject.toml`, and the SAM bootstrap, export, environment and synthetic fixture files. The packaged provisioner returned `ok: true`, `frozen: true` from `--self-check`; the packaged `uv` returned version 0.12.10. This confirms the shared Tauri resource map on macOS only. The normal release workflow pins `uv==0.12.19`; the locally available Homebrew binary was used solely for this package layout check. The temporary Tauri config edits were restored after the build.
- The first attempt using only Tauri's `--config` override failed the existing `build.rs` helper gate because that gate reads `src-tauri/tauri.conf.json` directly. The successful build temporarily patched that file and restored its original bytes in a `finally` block. This did not change the committed config.
- On the Windows CI runner, NSIS built `MangaCleaner_1.0.0-beta.2_windows-x86_64-setup.exe` (56,303,792 bytes in the inspected run). The 7-Zip inspection found the frozen provisioner, `uv`, four required VC++ runtime DLLs, SAM setup files, and a 436-byte updater signature. The frozen helper self-check passed. Run 36219174240 silently installed the actual installer to a path containing a space and `é` (`Manga Café smoke`), checked the installed app and helper executables, ran the installed provisioner self-check and `uv 0.12.19` with `PATH` reduced to Windows system directories, silently uninstalled, reinstalled, and uninstalled again. The hosted runner had developer tools installed globally, so this is not a clean OS test. The GUI, WebView2 loading, VC++ loader behavior, model setup, and updater were not exercised.
- On the Ubuntu 22.04 x64 CI runner, the build produced `MangaCleaner_1.0.0-beta.2_linux-x86_64.deb` (87,059,682 bytes) and `.AppImage` (161,958,392 bytes), plus updater signatures. Both packages were extracted and checked for executable provisioner/`uv` binaries and FLUX/SAM resources. Debian dependencies include `libayatana-appindicator3-1`, `libwebkit2gtk-4.1-0`, and `libgtk-3-0`. Neither package was launched in a desktop session.
- The CI Debian artifact was then installed with `apt-get install /tmp/mc.deb` in a fresh Ubuntu 22.04 `linux/amd64` container under QEMU on the M5 host. `dpkg-query` reported `manga-cleaner 1.0.0-beta.2 install ok installed`; `/usr/bin/manga-cleaner`, the frozen provisioner, and `manga-cleaner-uv` were executable; the FLUX and SAM source files were in `/usr/lib/Manga Cleaner`. The installed provisioner returned `ok: true, frozen: true` under `env -i` with a fresh home, and installed `uv` reported 0.12.19. `ldd /usr/bin/manga-cleaner` resolved GTK, WebKit2GTK 4.1 and other linked libraries. Removing and reinstalling the package succeeded. Under a temporary Xvfb and D-Bus session the app process survived 20 seconds until a controlled timeout; portal/FUSE warnings occurred, and no UI was inspected. This is an emulated container smoke check, not a real desktop installation.
