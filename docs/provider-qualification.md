This final cleanup exits status 0 without the earlier `ReleaseEpFactory ... Unknown exception` exit log; leaving the plugin registered until environment teardown caused that log even though inference succeeded and the process exited 0. ## Focused page 27 numerical question

On the **saved Pillow-prepared page-27 float tensor**, native Rust ORT WebGPU produced `+3.1382413e-6` at canvas `(x=162, y=463)`. The two restored pixels `(253,723)` and `(253,724)` are foreground, and the full WebGPU mask has **zero** changed pixels against saved PyTorch MPS. On that same input, ORT CPU produced `-1.213272e-5` and marked both pixels background; PyTorch CPU produced `+2.562094e-6`, and PyTorch MPS `+1.001358e-5`, marking both foreground. Thus WebGPU resolves this one CPU-specific sign discrepancy on the pinned Pillow input. This does **not** establish parity for the app's canonical decoded JPEG raster: the app JPEG decoder has a different prepared tensor on this page. See `spikes/sam-ts-l/results/native-page27-parity.md` and `spikes/sam-ts-l/results/native-rust-webgpu-page27-pillow.json`.

## CoreML status

The installed Python ORT runtime exposes `CoreMLExecutionProvider`, but full encoder+head CoreML is unqualified. With NeuralNetwork/ALL/dynamic-shape settings, encoder session construction exceeded 180 s and chain construction exceeded 180 s. The head alone loaded in 3.45 s, split 44 profiled node events to CoreML and 52 to CPU, ran in 0.65 s warm median, and differed from CPU ORT by four restored pixels. An MLProgram/GPU/static-shape encoder attempt exceeded 120 s. Provider availability and head execution do not prove a usable encoder path. ## Windows and Linux qualification plan

The available local machine is macOS/Apple M5 only. GitHub repository `k-omiq/manga-cleaner` reports **zero self-hosted runners** (`gh api repos/k-omiq/manga-cleaner/actions/runners`). CI uses GitHub-hosted `windows-latest` and Ubuntu runners for compile/tests, with no configured GPU hardware or provider benchmark job. Docker is installed locally but its daemon is unavailable; a container would not provide the missing Direct3D 12, Vulkan, NVIDIA, or AMD GPU qualification hardware. No paid cloud host was started.

Before any Windows/Linux provider is called qualified, run the pinned encoder and head on a matching physical GPU and installed runtime package. On Windows test DirectML with an NVIDIA, AMD, or Intel Direct3D 12 adapter as applicable; test CUDA on an NVIDIA machine with the matching CUDA/cuDNN runtime; test the WebGPU plugin on its Direct3D 12 backend. On Linux test WebGPU/Vulkan with a real adapter and Vulkan loader, CUDA on matching NVIDIA hardware, and MIGraphX only with a supported AMD ROCm machine. For each, record the runtime and plugin hashes/versions, actual adapter identity, discovered EP device, profiler node assignment for **both** graphs, CPU fallback count, page 07–09 and chapter mask/logit differences on identical prepared tensors, cold loads, warm chapter latency, process high-water, GPU memory high-water, and clean shutdown. A provider name in an availability list or a hosted CI green build is insufficient. Existing `spikes/sam-ts-l/benchmark.py` and `run_real_pages.py` provide the cross-platform Python probe; the native Rust probe documents the required session/device and profiling pattern. Hold Windows/Linux rows as unqualified until those measurements are present.

## Release disposition

The app-downloaded built-in WebGPU path executed both SAM graphs without CPU fallback and matched all 45 saved Pillow-input masks on the measured M5. Its roughly 6.3 s chain and near-6 GB sampled Metal high-water are the observed resource cost; the sampled Metal number may miss transients and overlaps RSS in unified memory. CPU remains the default for review. Explicit WebGPU PNG component writes are restricted by host identity, runtime SHA-256, full graph assignment, exact support approval, and source/plan rechecks. CPU, JPEG, longstrip, other Macs, Windows, and Linux remain unqualified for this write path.
